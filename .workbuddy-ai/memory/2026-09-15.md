### 解包/反混淆方法（可复用）
- asar 格式：`uint32(4)` + `uint32(jsonPaddedSize+8)` + `uint32(jsonPaddedSize+4)` + `uint32(jsonSize)` + JSON 索引；
  `base = 16 + jsonPaddedSize`，索引里的 offset 是相对 base。`unpacked:true` 的条目从 `app.asar.unpacked/` 读。
- 手写括号匹配切分 webpack bundle **会失败**（模板字符串/正则干扰）；改用 **acorn AST** 找
  "properties > 20 且 key 为数字字面量的 ObjectExpression" → 220 个模块，逐个 js-beautify。
- 业务代码全部集中在 module **5285**（369 KB）；bundle 末尾入口 IIFE 无法被 beautify 拆开，需字符串定位。

### 关键结论
- 主进程独占全部下载/校验/解压/启动逻辑；渲染进程（Next.js 14 静态导出）只做 UI + 登录 fetch。
- 索引 = Base64 → **AES-192-CBC**（key=ASCII `mJ9dH2bR7fT1zW4eQ6cY8a==` 24B，iv=ASCII `aP3sD8fG0hJ6kL9z` 16B）→ CSV。
- 域名：`api-grp.manjuu.com` / `api-grp-l2.manjuu.com`（双线），实际由 `getLauncherConfig` 下发。
- 签名 `extApi3(timestamp + canonicalPayload + utoken)`，在原生 `napi-cutils` 内，未逆向。
- 两种安装模式：`SLICE=1`（分片→合并 game.zip→解压，需 2× 空间）/ `REALITY=2`（直下最终文件，1.1×）。
- 游戏账号通过环境变量 `manjuu_user_info` / `manjuu_channel_info` 传给游戏进程（非命令行）。
- 自更新是「版本目录并列」结构：`../_temp` 下载 → `../<version>` 解压 → 迁移 HKLM 注册表/快捷方式 → 换进程；
  互斥体/管道名不含版本号，切换前必须 destroyMutex + closeServer。
- 关键阻塞项（对插件复刻）：`cutils.extApi1`（解 app_config.dat）、`extApi3`（签名）需逆向或复用官方 napi-cutils。

## 【续】原生模块 `cutils.node` 完整逆向（已完成，阻塞项全部解除）

**产出**：`docs/12-原生模块逆向与CSharp复刻.md`（含可直接编译的 C# 类 `CUtilsPortable`）
+ `docs/reference/native-analysis/`（可复现工具链 + `symmap.json` 符号表）

### 破题方法（强烈推荐复用到其它 N-API 原生模块）
1. **N-API 的 ABI 稳定性**：Electron 编译的 `.node` **可直接被普通 Node 22 `require`**，
   不必匹配 Electron ABI → 先拿到全部真实输入/输出（本次一切结论都源于此）。
2. **把随机系统变确定系统**：`extApi4` 输出非确定（随机 IV）。发现它其实有第 3 个参数；
   传入 16 字节 IV 后输出变确定 → 算法立刻可锁定。**这是本次最关键的一步。**
3. **现象先行、假设收敛**：「输出恒长 + 非确定」直接排除「直接加密输入」和「纯哈希」，
   把范围压到「固定明文 + 随机 IV」；再用 `pwdKey` 补零作密钥试解密密文，一步得到 `MD5("")`。
4. **静态交叉验证流水线**（脚本都在 `docs/reference/native-analysis/`）：
   - 解析 PE 导入表 → 判断静态链接了 OpenSSL 3.x + libcurl；
   - 解析 `.pdata` → 17 182 个函数边界；
   - 扫描 RIP-relative `lea` → 定位引用 `"extApi1"` 字符串的 napi 属性描述符；
   - thunk 链回溯（`0x18012ef80 → 0x18012a080 → 0x180134cd0`）找到真实现；
   - **用 OpenSSL 的 `ERR_*` 错误字符串给静态链接函数自动命名（643 个）** →
     「一堆 `call 0x...`」变成可读调用链。这个技巧通用性极强。

### 最终算法（已 15 项断言全通过）
- `extApi1(path)` = **AES-256-CBC**，key = ASCII `5f109ac9d64946e191c354d524bfe590`（硬编码），
  IV = 文件前 16 字节，密文 = 其余，PKCS#7。→ `res/app_config.dat` 192B = 16 IV + 176 CT。
- `extApi2(sk, appId, channelCode)` = 纯字段赋值，无加密。
- `extApi3(payload)` = **`MD5(payload + appId + channelCode + secretKey)`** 小写 hex（顺序敏感，已验证）。
- `extApi4(pwd, pwdKey[, iv16])` = `Base64( ASCII(Base64(AES256CBC(md5hex(UTF8(pwd)), key=pwdKey[:32]补0, iv))) + iv原始字节 )`。
  输出恒 108 字符（明文恒 32B → CT 恒 48B）；`pwdKey` 是**对称密钥**不是 RSA 公钥。

### 解出的渠道配置（CN / C000）
`launcherId=a35deadb9f8846c9ad69bc2f4e299b8c` `gameId=35` `appId=354` `channelCode=C000`
`secretKey=20bccb31-fb57-4683-b6d8-6314d43811f2`

### 结论
**C# 插件不再需要 `cutils.node` / OpenSSL / Node**，四个接口均可用 .NET BCL 纯托管实现。
仍需外部输入：`res/app_config.dat`（渠道数据无法自造）与 `svrConfig.pwdKey`（服务端下发）。

### ⚠️ 本机构建的坑（重要，可复用）
本机是**被裁剪过的 Windows 环境**：注册表里 `HKCU\Environment` / `HKLM\...\Session Manager\Environment`
**只有 18 个变量**，没有 `APPDATA` / `ProgramData` / `ALLUSERSPROFILE` / `USERPROFILE`。
导致 NuGet 的 `XPlatMachineWideSetting..ctor()` → `NuGetEnvironment.CalculateFolderPath`
拿到 null → 任何 `dotnet build`（连 `dotnet new classlib` 也一样）都报：

```
NuGet.targets(782,5): error : Value cannot be null. (Parameter 'path1')
```

**设环境变量没用**（试过 APPDATA/ProgramData/ALLUSERSPROFILE/USERPROFILE，无效）。
`cmd.exe` 被沙箱拦截，`csc.dll` 被沙箱拦截（"compiles arbitrary C# code"），
PowerShell 工具**能执行但拿不到 stdout**（要重定向到文件再读）。

**解决方案 = 完全绕开 NuGet**，用这三个 MSBuild 属性：

```bash
dotnet build <proj> -c Release \
  -p:RestoreProjectStyle=Unknown \      # 让 _GetRestoreSettings 条件为假 → 不再触发 XPlatMachineWideSetting
  -p:SkipResolvePackageAssets=true \    # 跳过 ResolvePackageAssets → 不再报 NETSDK1004
  -p:GenerateDependencyFile=false       # 跳过 GenerateDepsFile（它也要读 project.assets.json）
```

- `RestoreProjectStyle=Unknown` 单独用会报 NETSDK1004（restore 说"无可还原的包"、不生成 assets 文件）。
- 加了 `SkipResolvePackageAssets` 后错误转移到 `Microsoft.NET.Sdk.targets(308,5)` 的 `GenerateDepsFile`。
- 再加 `GenerateDependencyFile=false` → **库项目构建成功**。
- 框架引用（`ProcessFrameworkReferences` / `ResolveTargetingPackAssets`）**不依赖** assets 文件，所以
  `System.Text.Json` / `Microsoft.Win32.Registry` / `System.Net.Http` 等都能正常引用。
- 唯一需要 NuGet 的包是 `Microsoft.Extensions.Logging.Abstractions`，改为在
  `Directory.Build.props` 里按 `LocalNoNuGetBuild=true` 条件加 `<Reference>` + `HintPath` 指向
  `~/.nuget/packages/...`（`Private=false`，宿主已提供）。该文件默认 inert，不影响正常构建。

### 编译期修掉的真实错误（记录备查）
1. `Utils/AzurPromiliaAccount.cs` 命名空间手误 `Azurpromilia`（小写 p）→ 调用方全部 CS0246。

## 修复 pwdlogin `code=2 MD5校验错误`（线上实测确认）

### 现象
线上运行时日志：
```
[AzurPromilia] pwdlogin returned no usable session (code=2, msg=MD5校验错误).
```

### 定位方法：线上差分探测（不是读代码猜）
写了 `tools/probe/probe_sign.py`，用真实渠道密钥向线上接口发**只改一个变量**的变体请求，
直接观察服务端接受哪一种。结论（`docs/03` §9 有完整表格）：

| 请求 | 签名覆盖的内容 | 服务端返回 |
| --- | --- | --- |
| GET config | `""` + utoken 头 `""` | `code=0` ✅ |
| GET config | `"null"` + utoken 头 `"null"` | `code=0` ✅ |
| GET config | `""` + utoken 头 `"null"` | `code=2` ❌ |
| POST pwdlogin | `""`（= 旧代码，照搬 GET 写法签空 query） | `code=2 MD5校验错误` ❌ |
| **POST pwdlogin** | **`body`** | **`code=11017 通行证不存在`** ✅ 签名通过 |
| POST pwdlogin | `"0"×32` 对照项 | `code=2` ❌ |

### 两条规则（都已实测）
1. **POST 的签名覆盖请求体 JSON 字符串本身**，不是 query（POST 的 query 恒为空）。
   → 旧代码 `BuildSignedHeaders(data)` 对 POST 传空字典，签的是 `timestamp + "" + utoken`，必挂。
2. **签名里的 utoken 必须与 `utoken` 请求头逐字节一致**。服务端直接把请求头原值拼进待签名串。
   空串和字面量 `"null"` 两种约定都能过，但**不能混用**。本插件统一用空串。

### 另外两个容易踩的坑
- **登录接口不在业务域名上**：`/passportv2/client/**` 必须走 `launcherInitConfig.user.domains`
  = `https://passport-grp.manjuu.com`。发到 `api-grp.manjuu.com` 得到的是 **HTTP 404**（不是 code=2）。
  → 404 = 域名错；code=2 = 签名错；其他 code = 业务错。
- `code=2` 与密码/账号**完全无关**，服务端在验签阶段就拒了。看到 code=2 不要去怀疑 extApi4。

### 代码改动
- `Management/Api/AzurPromiliaApiHelper.cs`
  - 新增 `ComposeSigningPayload`（签名公式唯一出处）、`BuildGetSigningPayload`、
    `BuildPostSigningPayload`（后两个 internal，供测试断言）。
  - `BuildSignedHeaders(string signedPayload)` 重载；`ApplyHeaders` 增加 string 重载。
  - **`PostLoginAsync` 改为 `ApplyHeaders(request, body)`**（原来传空字典）。这是真正的修复点。
  - 请求体只序列化一次，签名与发送用同一字符串；`Content-Type` 改为裸 `application/json`。
  - timestamp 用 `InvariantCulture` 格式化。
- `Management/Api/AzurPromiliaLoginService.cs`
  - 新增 `LogLoginFailure`：`code=2` 单独报 **Error** 并明确写出"这是插件缺陷不是密码问题"，
    其余 code 仍走 Warning。避免下次再被误判。
- `AssemblyInfo.cs`：加 `InternalsVisibleTo("AccountResolutionTests")`。
- `tests/AccountResolutionTests/Program.cs`：新增 10 项签名断言（含已知答案向量，
  向量由 Python 独立算出）+ 3 项 `--live` 端到端断言。
  `--live` 用**真实** `AzurPromiliaApiClient` 打线上，断言 pwdlogin 返回码 ≠ 2。
- `run-account-test.sh`：支持透传参数（`--live`）。
